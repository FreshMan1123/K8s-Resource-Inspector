# K8s-Resource-Inspector 项目规则

## 核心原则：先方案后实施

> **最重要规则**：任何代码修改、文件创建或结构调整，无论大小，都必须先提交方案并获得明确批准，然后再实施。

## TDD严格执行规则 (新增)

### 功能全景规划原则
- **功能清单先行**：任何新功能开发前，必须先列出完整的功能清单和所有计划实现的子功能
- **测试骨架预留**：为所有计划功能创建测试骨架，包括：
  - 核心功能测试（主要业务逻辑）
  - 边界条件测试（空值、极值、边界情况）
  - 错误处理测试（网络错误、权限错误、数据错误）
  - 集成场景测试（组件间交互、真实环境模拟）
  - 配置选项测试（不同参数组合的效果）
- **渐进式实现**：按优先级实现功能，每个功能必须通过对应测试后才能进行下一个

### 测试先行强制规则
- **严格禁止跳过测试**：不允许使用 `t.Skip()` 除非有明确的技术限制（如需要特殊硬件）
- **红-绿-重构循环**：必须严格遵循 Red(失败测试) -> Green(最小实现) -> Refactor(重构) 循环
- **测试必须失败**：新功能的测试在实现前必须失败（Red阶段），证明测试有效
- **最小实现**：实现刚好让测试通过的最小代码（Green阶段），避免过度设计
- **重构验证**：重构后所有测试必须继续通过，确保功能不被破坏

### 集成测试完整性要求
- **场景覆盖**：集成测试必须覆盖所有用户使用场景，包括正常和异常情况
- **环境模拟**：测试应模拟真实环境条件（网络问题、权限问题、资源不足等）
- **配置测试**：测试不同配置选项的组合效果，确保所有配置都被验证
- **错误路径测试**：测试各种错误情况的处理，确保系统在异常情况下的稳定性
- **性能边界测试**：测试系统在负载边界的表现

- [ ] 我已对方案进行了全面的自我评估，包括技术可行性、影响范围、兼容性等

## 详细规则

### 1. 任务处理流程
1. **初步分析**：阅读相关代码，理解问题本质，识别需要进一步了解的上下文信息
2. **信息收集**：提出针对性问题，获取缺失的上下文信息，基于获取的信息完善对问题的理解。
3.**反问用户补充情况**：通过反问用户想要了解的情况，来补充对代码情况的了解
4. **方案提交**：提供详细方案，包括修改内容，提供全面的自我评估
5. **等待批准**：明确等待用户批准
6. **实施方案**：获得批准后，严格按照批准的方案实施
7. **完成通知**：实施完成后，明确告知"任务已完成"

### 2. 文档编辑规则
- **保留原有内容**：编辑文档时，不删除原有内容，只做补充和调整
- **明确标注变更**：清晰说明哪些是新增内容，哪些是调整内容

### 3. 代码修改规则
- **严格遵守范围**：只修改指定文件和功能
- **发现问题提建议**：发现其他问题时，提出建议而非直接修改
- **必须完整理解代码**：在提交方案前，必须完整阅读与任务相关的所有代码，确保完全理解代码逻辑和结构
- **一字一句阅读理解**：对与方案直接相关的模块代码，必须一字一句阅读理解，不能仅凭猜测或假设

### 4. 交互规范
- **使用中文**：所有交互、注释使用中文
- **明确当前状态**：每次交互开始时，说明当前是"方案提议阶段"还是"实施阶段"
- **不自行扩展任务**：完成一项任务后等待新指示，不自动开始下一项
- **编译运行由用户执行**：AI不直接执行编译和运行操作，而是提供完整的命令供用户执行，包括：
  - 编译命令：`cd code && go build -o inspector.exe ./cmd/inspector/`
  - 运行命令：`cd code && ./inspector.exe [具体参数]`
  - 其他必要的环境设置或依赖安装命令
- **批判性思考用户想法**：当用户提出想法或建议时，应以最佳实践的角度进行评判，而不是直接同意。需要分析优缺点，并给出基于行业最佳实践的专业意见，必要时应提出更好的替代方案

### 5. 测试策略：功能测试 + 集成测试 (F+I Testing)

#### 核心测试原则
- **用户场景驱动**：所有测试都基于真实用户使用场景，模拟实际操作流程
- **功能完整性优先**：确保每个功能都能正常工作，重点验证输入输出正确性
- **组件协同验证**：确保组件间能正确协作，验证数据流转的准确性

#### 测试类型定义 (符合工具类软件最佳实践)
- **功能测试** (70%)：
  - 测试单个功能的完整流程，从输入到输出的全链路验证
  - 模拟真实用户操作，验证CLI命令的正确执行
  - 测试文件命名：`xxx_functional_test.go`
  - 放置位置：`code/test/` 目录下，一个模块一个测试文件
- **集成测试** (30%)：
  - 测试多组件协同工作，验证组件间的数据传递和状态同步
  - 测试系统级的端到端流程，模拟完整的业务场景
  - 包含系统集成测试：`system_integration_test.go`

#### 不采用的测试类型 (基于项目特点)
- **单元测试**：对于CLI工具，功能测试已能充分验证代码正确性
- **性能测试**：巡检工具重点在功能正确性，非高并发性能场景
#### 测试用例设计原则
- **真实场景模拟**：每个测试都应模拟用户的真实使用场景
- **完整流程验证**：从命令输入到结果输出的全链路测试
- **边界和异常处理**：测试各种边界条件和错误情况
- **配置组合测试**：测试不同配置参数的组合效果

#### 测试文件组织规范
```
code/test/
├── vulnerability_functional_test.go    # 漏洞扫描功能测试
├── security_functional_test.go         # 安全分析功能测试
├── resource_functional_test.go         # 资源管理功能测试
├── cluster_functional_test.go          # 集群管理功能测试
├── system_integration_test.go          # 系统集成测试（全组件联动）
└── testdata/                           # 测试数据
    ├── mock_responses/                 # 模拟响应数据
    ├── test_configs/                   # 测试配置文件
    └── expected_outputs/               # 预期输出结果
```

#### 测试执行命令
- **功能测试**：`cd code && go test ./test/*_functional_test.go -v`
- **集成测试**：`cd code && go test ./test/system_integration_test.go -v`
- **全部测试**：`cd code && go test ./test/... -v`
- **测试覆盖率**：`cd code && go test ./test/... -cover -v`
#### 测试数据管理
- **结构化存储**：使用JSON/YAML文件存储测试数据，便于维护和版本控制
- **场景分类**：测试数据按正常场景、边界场景、异常场景分类组织
- **Mock策略**：使用Mock对象模拟外部依赖（K8s API、网络请求等）

#### 测试质量要求
- **功能覆盖率**：功能测试必须覆盖所有用户可操作的功能点
- **场景完整性**：集成测试必须覆盖主要的业务流程和用户场景
- **代码质量**：测试代码必须与实现代码遵循相同的质量标准
- **可维护性**：测试代码应易于理解、修改和扩展

#### 测试执行最佳实践
- **独立性**：每个测试应该独立运行，不依赖其他测试的执行结果
- **可重复性**：测试结果应该稳定，多次运行结果一致
- **明确性**：测试失败时应该能清楚地指出问题所在
- **真实性**：测试环境应尽可能接近真实使用环境

#### 系统集成测试特殊要求
- **端到端验证**：模拟用户使用二进制包进行完整操作流程
- **真实环境模拟**：在可能的情况下使用真实的K8s集群进行测试
- **数据流验证**：验证从输入到输出的完整数据流转过程
- **错误恢复测试**：测试系统在各种异常情况下的恢复能力

### 6. 最佳实践评估
- **方案评估**：在提交方案时，评估方案是否符合Go语言和Kubernetes开发的最佳实践
- **代码质量检查**：评估代码的可读性、可维护性、性能和安全性
- **架构合理性**：评估修改是否符合项目的整体架构设计
- **依赖管理**：评估新增依赖的必要性和兼容性
- **错误处理**：确保代码中有完善的错误处理机制
- **日志记录**：确保关键操作有适当的日志记录

### 7. 方案阶段信息收集规范
- **必须主动收集上下文**：在提交方案前，必须主动提问以获取未能从代码中直接获得的上下文信息
- **问题类型**：问题应主要集中在以下几类：
  - **业务背景问题**：该功能的业务目的和用户场景是什么？
  - **历史决策问题**：为什么之前的代码是这样设计的？
  - **未来规划问题**：该模块未来有什么扩展计划？
  - **使用场景问题**：代码在实际环境中如何被使用？
  - **特殊约束问题**：是否有特殊的技术或业务约束需要考虑？
  - **优先级问题**：在多个可能的解决方案中，哪些因素更重要？
  - **团队偏好问题**：团队在编码风格、设计模式等方面有什么偏好？
  - **未记录需求问题**：是否有未在代码或文档中体现的隐含需求？
- **避免转嫁评估工作**：不应询问那些应由AI自己评估的问题，如技术可行性、代码影响范围等
- **问题精确性**：问题应该具体明确，避免过于宽泛的问题
- **问题必要性**：只询问对方案制定确实必要的信息，避免过多不必要的问题

### 8. 方案自我评估规范
- **技术可行性评估**：必须评估方案的技术可行性，包括是否符合语言特性、框架限制等
- **影响范围评估**：必须分析代码修改的影响范围，包括直接和间接影响的模块
- **向后兼容性评估**：必须评估方案是否保持向后兼容性，或者明确指出不兼容的变更
- **性能影响评估**：必须评估方案对系统性能的潜在影响
- **安全性评估**：必须评估方案是否引入安全风险
- **可维护性评估**：必须评估方案是否提高或降低代码的可维护性
- **测试策略评估**：必须提出合适的测试策略，确保修改被充分测试

### 9. 项目规则补充说明
- **优先级原则**：
  - 功能实现优先于其他考量
  - 在关键决策点主动询问用户进行权衡
  - 严格遵循每一条项目规则，不擅自灵活处理
- **文档与注释要求**：
  - 文档应简明扼要，避免冗长但确保必要信息完整
  - 为每个函数提供详细注释，确保代码可读性和可维护性
- **错误处理流程**：
  - 在处理错误前先提供方案供用户评估
  - 尽早处理发现的技术债务，避免后期偿还困难
- **方案评估标准**：
  - 技术正确性
  - 可扩展性
  - 符合行业最佳实践
- **跨模块修改协调**：
  - 涉及多个模块时，一次性提供完整的总体设计协调方案
  - 在用户批准后，按模块拆分逐一实施
- **功能与性能平衡**：
  - 优先考虑功能实现，性能优化可以后置
- **兼容性要求**：
  - 确保代码在Windows、Linux和macOS平台上兼容
  - 进行重大更改时应谨慎评估影响范围
  - 提供更改后的预期结果和回滚方案
- **代码审查与实现决策**：
  - 实施完成后进行自我审查，解释关键实现决策
  - 评估代码是否符合最佳实践
- **文档更新要求**：
  - 代码变更时同步更新相关文档
  - 确保文档与代码保持一致
- **规则适用范围**：
  - 项目规则适用于所有情况，除非用户特殊说明
- **反馈处理方式**：
  - 收到反馈时先进行讨论
  - 从最佳实践角度评估反馈的合理性
  - 在达成共识后再进行修改
- **优先级排序**：
  - 功能正确性 > 代码质量 > 性能
- **规则演进**：
  - 始终以最新的项目规则为准

## 违规后果

如违反以上规则，特别是"先方案后实施"原则，将：
1. 立即停止当前操作
2. 明确承认违规行为
3. 重新按正确流程执行

- **优先级排序**：
  - 功能正确性 > 代码质量 > 性能
- **规则演进**：
  - 始终以最新的项目规则为准

## 违规后果

如违反以上规则，特别是"先方案后实施"原则，将：
1. 立即停止当前操作
2. 明确承认违规行为
3. 重新按正确流程执行
